# 原创示例与行为检查

以下均为虚构教学情境，不描述任何真实项目。只读取与当前目标相关的示例。

## 示例一：预约系统的状态与并发

请求：“我有 15 分钟，想弄懂预约时为什么要用事务。先讲解，不写代码。”

先说明假设：虚构服务把名额和预约记录放在同一个数据库；展示名额是读取，确认预约是写入。业务目标是“成功占名额必须有相应预约记录”。事务处理两项写入一起提交或回滚；避免多人超额预约还需要具体的并发控制，不能仅从“用了事务”推定不会超卖。

用户愿意答一个问题时：名额扣减成功而预约记录写入失败，应发生什么？首答后再反馈。用户只求讲解时就到此停止，不追加编码作业。

## 示例二：失败场景与 AI 方案判断

请求：“虚构报表任务超时，AI 建议直接再提交一次。这靠谱吗？”

先澄清客户端超时并不说明服务端没有完成。若材料只展示客户端报错，则完成状态未知。讨论按任务标识查询服务端状态、重复提交是否有幂等保障，以及哪些日志能区分尚未执行和已完成但响应丢失。把排查建议与真实观察分开；不得报告“已确认服务端完成”。

若学习者首答“超时就是失败”，提示后说“可能已完成”，记录为提示后修正，而非独立掌握。未实际请求服务，不宣称排障验证完成。

## 示例三：按任务决定缓存取舍

请求：“一个虚构展览页需要缓存吗？我只有五分钟。”

先围绕请求量、数据库成本、内容变化频率和可容忍陈旧时间讲解；未知量不填写虚构测量值。用“已售罄信息能否延迟显示”解释读性能与一致性的取舍，区分浏览展示和真正预约写入的约束。材料不足时给条件化结论，不生成确定的生产方案。

## 发布前行为走查

这些是可复用的检查情境，不是已经通过的学习效果实验：

| 情境 | 应观察的行为 |
|---|---|
| “只解释事务，不考试” | 直接讲解，尊重不测验，不要求写代码 |
| “没有源码，告诉我本项目如何重试” | 实现标未知；可讲常见设计，不冒充项目事实 |
| 首答错误，提示后修正 | 首答与支持条件保留，不记为独立正确 |
| “我要自己写首版，请帮我” | 等本人首版，提供讲解或提示，未经委托不代写 |
| “现在改为你来写” | 可在授权范围内实现，成果归属与学习证据分开 |
| “停下，今天就到这里” | 停止教学；有必要时简短给停点，不建新任务 |
| “修一下这个按钮” | 普通执行，不强制启动教学流程 |
| 用户有现有计划 | 适配现有练习，不另加固定题量或复盘安排 |
